● Vamos para a Etapa 4: Fluxo de requisições e de dados.

  Pergunta 10: Vou descrever o fluxo de uma requisição típica. Me diga se está
  correto:

  Fluxo de requisição (ex: aluno acessa uma aula):
  1. Cliente envia request HTTP para Express.js
  2. Middleware de autenticação valida token (JWT)
  3. Middleware de autorização verifica papel e contexto (ex: aluno matriculado
  naquele curso)
  4. Router direciona para o controller do módulo correto
  5. Controller chama o use case (camada de aplicação - hexagonal)
  6. Use case aplica regras de negócio (ex: verifica desbloqueio do módulo,
  matrícula ativa, carência)
  7. Use case chama o repositório (port/adapter) para persistir ou consultar no
  PostgreSQL
  8. Resposta retorna pelo mesmo caminho com HTTP caching headers

  Fluxo de dados para upload de mídia:
  1. Cliente envia arquivo via multipart/form-data
  2. Middleware valida tamanho (até 1 GB) e tipo (vídeo/áudio)
  3. Módulo Media faz upload para disco local (dev) ou S3 (produção)
  4. Referência do arquivo é salva no PostgreSQL vinculada à aula
  5. Streaming é servido via endpoint dedicado (dev) ou URL pré-assinada do S3
  (produção)

  Esses fluxos estão corretos? (sim/ajuste)

  Fluxo de dados para upload de mídia (revisado):
  1. Cliente inicia upload enviando metadados (nome, tamanho, tipo)

  6. Referência do arquivo é salva no PostgreSQL vinculada à aula
  7. Streaming é servido via endpoint dedicado (dev) ou URL pré-assinada do S3
  (produção)

● Vamos para a Etapa 10: Riscos arquiteturais e mitigação.

  Pergunta 21: Identifiquei os seguintes riscos arquiteturais. Me diga se
  concorda ou gostaria de ajustar:

  Risco 1: Upload de arquivos grandes (até 1 GB) sobrecarregando o servidor
  - Probabilidade: Alta
  - Impacto: Degradação de performance para todos os usuários durante uploads
  - Mitigação: Limitar uploads concorrentes por usuário; migração para S3 com
  upload direto do cliente (presigned URL) em produção
  - Contingência: Rate limiting agressivo no endpoint de upload

  Risco 2: Monolito modular com acoplamento crescente entre módulos
  - Probabilidade: Média
  - Impacto: Dificuldade de manutenção e evolução a médio prazo
  - Mitigação: Arquitetura hexagonal com boundaries claros; code reviews focados
   em dependências entre módulos
  - Contingência: Extração de módulos críticos para microsserviços

  Risco 3: PostgreSQL como ponto único de falha
  - Probabilidade: Média
  - Impacto: Indisponibilidade total do sistema
  - Mitigação: Backups automatizados; connection pooling (PgBouncer)
  - Contingência: Restore de backup; futura adoção de réplica de leitura

  Risco 4: Cálculos de progresso e notas em tempo real sob alta carga
  - Probabilidade: Média
  - Impacto: Latência elevada em endpoints de progresso e desbloqueio de módulos
  - Mitigação: Queries otimizadas com índices adequados; HTTP caching
  - Contingência: Introdução de cache (Redis) ou materialização de progresso em
  tabela dedicada
