● Ótimo. Vamos para a Etapa 4: Fluxos detalhados e diagramas.

  Vou detalhar o fluxo principal primeiro. Começando pelo mais central:

  Fluxo 1: Cadastro de usuário (Admin)
  1. Admin autenticado envia POST com nome, email, senha e papéis
  2. Middleware de autenticação valida JWT + sessão ativa no banco
  3. Middleware RBAC verifica que o usuário tem papel "admin"
  4. Controller repassa para o use case CreateUser
  5. Use case valida: nome (max 100 chars), email (formato válido), senha
  (política), ao menos 1 papel válido
  6. Use case verifica unicidade do email no banco
  7. Use case gera hash da senha (bcrypt/argon2)
  8. Use case persiste o usuário com situação "ativo" e papéis atribuídos
  9. Retorna 201 com dados do usuário (sem senha)

  Fluxo 2: Login (qualquer usuário)
  1. Usuário envia POST com email e senha
  2. Use case busca usuário por email
  3. Se não encontrado, retorna erro genérico (sem revelar se email existe)
  4. Se encontrado, verifica hash da senha
  5. Se senha incorreta, retorna mesmo erro genérico
  6. Se conta bloqueada, retorna erro de conta bloqueada
  7. Se tudo válido, cria sessão no banco e emite access token + refresh token
  8. Retorna 200 com tokens

  Fluxo 3: Gestão de papéis (Admin)
  1. Admin autenticado envia PATCH com papéis a adicionar/remover
  2. Middlewares de autenticação e RBAC executam
  3. Use case valida que ao menos 1 papel restará após a operação
  4. Use case atualiza papéis do usuário
  5. Retorna 200 com dados atualizados

  Fluxo 4: Bloqueio/desbloqueio (Admin)
  1. Admin autenticado envia PATCH com nova situação (bloqueado/ativo)
  2. Middlewares de autenticação e RBAC executam
  3. Use case atualiza situação do usuário
  4. Se bloqueio: use case invalida todas as sessões ativas do usuário
  5. Retorna 200 com dados atualizados

  Fluxo 5: Isolamento de dados (Aluno)
  1. Aluno autenticado faz GET em recurso próprio (ex: suas matrículas)
  2. Middlewares de autenticação e RBAC executam
  3. Use case aplica filtro ACL: só retorna dados do próprio usuário
  4. Se tentativa de acesso via URL a recurso de outro aluno, retorna 403

  Fluxos alternativos e exceções:
  - Email duplicado no cadastro: rejeita com 409 Conflict
  - Senha fora da política: rejeita com 422 e lista de critérios não atendidos
  - Nenhum papel selecionado: rejeita com 422
  - Tentativa de remover último papel: rejeita com 422
  - Token expirado: retorna 401, cliente usa refresh token
  - Refresh token inválido/expirado: retorna 401, cliente precisa fazer login
  novamente
  - Sessão invalidada (bloqueio): retorna 401 na próxima requisição

  Gostaria de algum diagrama de sequência para algum desses fluxos, ou os fluxos
   estão completos para seguir em frente?

  ---
  1. POST /v1/auth/login
  - Público (sem autenticação)
  - Request: { "email": "string", "password": "string" }
  - Response 200: { "access_token": "string", "refresh_token": "string", 
  "expires_in": 900 }
  - Erros: 401 (credenciais inválidas), 403 (conta bloqueada)

  2. POST /v1/auth/refresh
  - Público (sem autenticação, usa refresh token no body)
  - Request: { "refresh_token": "string" }
  - Response 200: { "access_token": "string", "refresh_token": "string", 
  "expires_in": 900 }
  - Erros: 401 (refresh token inválido/expirado)

  3. POST /v1/auth/logout
  - Autenticado (qualquer papel)
  - Header: Authorization: Bearer <access_token>
  - Response: 204 No Content
  - Efeito: invalida a sessão no banco

  4. POST /v1/users
  - Autenticado, papel: admin
  - Request: { "name": "string", "email": "string", "password": "string", 
  "roles": ["aluno", "professor"] }
  - Response 201: { "id": "uuid", "name": "string", "email": "string", "roles": 
  ["aluno", "professor"], "status": "ativo", "created_at": "ISO8601" }
  - Erros: 409 (email duplicado), 422 (validação: senha, papéis, nome)

  5. PATCH /v1/users/:id/roles
  - Autenticado, papel: admin
  - Request: { "roles": ["aluno", "professor", "tutor"] }
  - Response 200: { "id": "uuid", "name": "string", "email": "string", "roles": 
  [...], "status": "string", "updated_at": "ISO8601" }
  - Erros: 404 (usuário não encontrado), 422 (lista vazia de papéis)

  6. PATCH /v1/users/:id/status
  - Autenticado, papel: admin
  - Request: { "status": "bloqueado" | "ativo" }
  - Response 200: { "id": "uuid", "name": "string", "email": "string", "roles": 
  [...], "status": "bloqueado", "updated_at": "ISO8601" }
  - Erros: 404 (usuário não encontrado)

  7. GET /v1/users/:id
  - Autenticado, papel: admin (qualquer usuário) ou próprio usuário (seus dados)
  - Response 200: { "id": "uuid", "name": "string", "email": "string", "roles": 
  [...], "status": "string", "created_at": "ISO8601", "updated_at": "ISO8601" }
  - Erros: 403 (acesso negado), 404 (não encontrado)

  8. GET /v1/users
  - Autenticado, papel: admin
  - Response 200: { "data": [User[]], "total": number, "page": number, 
  "per_page": number }
  - Suporta paginação e filtros (por papel, situação, nome)

● Vamos para a Etapa 7: Observabilidade.

  Métricas:
  - auth.login.total (counter) - total de tentativas de login (tags:
  success/failure)
  - auth.login.blocked (counter) - tentativas de login em contas bloqueadas
  - auth.token.refresh.total (counter) - total de refresh token requests (tags:
  success/failure)
  - auth.session.active (gauge) - sessões ativas no banco
  - users.created.total (counter) - usuários criados
  - users.blocked.total (counter) - usuários bloqueados
  - users.endpoint.duration (histogram) - latência por endpoint (tags: method,
  route, status)

  Logs (JSON estruturado):
  - Campos padrão: timestamp, level, request_id, user_id, module: "user",
  action, message
  - Login bem-sucedido: { action: "login_success", user_id, roles }
  - Login falho: { action: "login_failure", reason: "invalid_credentials" | 
  "blocked_account" } (sem logar email para proteger PII)
  - Usuário criado: { action: "user_created", target_user_id, roles, created_by 
  }
  - Usuário bloqueado: { action: "user_blocked", target_user_id, 
  sessions_invalidated: number, blocked_by }
  - Sessão invalidada: { action: "session_invalidated", target_user_id, reason: 
  "block" | "logout" }
  - Acesso negado: { action: "access_denied", target_resource, reason }

  Tracing (OpenTelemetry):
  - Spans principais:
    - auth.middleware - validação JWT + consulta sessão
    - rbac.middleware - verificação de papel
    - usecase.{create_user|login|block_user|update_roles} - lógica de negócio

● Vamos para a última etapa: Etapa 10: Riscos e mitigação.

  Risco 1: Consulta ao banco a cada requisição autenticada (validação de sessão)
  - Probabilidade: Média
  - Impacto: Aumento de latência em todos os endpoints autenticados sob alta
  carga
  - Mitigação:
    - Query leve por ID de sessão com índice dedicado
    - Connection pooling via PgBouncer
    - Monitorar latência do span auth.middleware via tracing
  - Plano de contingência: Introduzir cache de sessão em memória (ex: Redis) com
   TTL curto (30s), aceitando janela de delay no bloqueio

  Risco 2: Ataques de força bruta no endpoint de login
  - Probabilidade: Alta
  - Impacto: Comprometimento de contas, sobrecarga no banco (hashing argon2 é
  CPU-intensivo)
  - Mitigação:
    - Rate limiting de 20 req/s para endpoints não autenticados (conforme HLD)
    - Mensagem genérica no login (não revela se email existe)
    - Logs de tentativas falhas com alerta em taxa > 50% em 5 min
  - Plano de contingência: Implementar bloqueio temporário por IP ou por conta
  após N tentativas falhas

  Risco 3: Vazamento de sessões (sessões órfãs no banco)
  - Probabilidade: Média
  - Impacto: Crescimento da tabela de sessões, degradação de queries
  - Mitigação:
    - TTL na sessão igual ao refresh token (7 dias)
    - Job periódico para limpar sessões expiradas
    - Métrica auth.session.active com alerta de crescimento anômalo
  - Plano de contingência: Truncar sessões expiradas manualmente; adicionar
  índice parcial em sessões ativas

  Risco 4: Binding nativo do argon2 causa problemas em diferentes ambientes
  - Probabilidade: Baixa
  - Impacto: Falha no build ou deploy em ambientes sem dependências nativas
  - Mitigação:
    - Docker como ambiente padrão (dependências controladas)
    - Testar build no CI com a mesma imagem Docker de produção
  - Plano de contingência: Fallback para bcrypt (puro JS, sem binding nativo)

  Esses riscos estão completos ou gostaria de adicionar/ajustar algo?
